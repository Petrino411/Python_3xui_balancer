# xray-client-balancer

Раскладывает клиентов панели **3x-ui** по балансировщикам **Xray**: у каждой группы
свой основной исходящий, а если он перестал работать — трафик уходит на общий резерв.

```
клиент ──> client-balancer-1 ──> sub1-mskserv ─┐
       ──> client-balancer-2 ──> sub2-cringe  ─┼─ при недоступности ──> sub1-tls-stock-tls
       ──> client-balancer-3 ──> sub3-riga    ─┘                        (общий fallback)
```

Кто в какой группе, сервис помнит в SQLite по внутреннему id клиента панели (id не
меняется, если клиенту поправили email). Поэтому перезапуск сервиса раскладку не
меняет: клиент переезжает только по вашей команде — `move`, `rebalance` или `reset`.

Что делает сервис сам: читает список клиентов панели, раздаёт новые по группам
(максимально ровно, без случайности), держит свои правила в `routing` и следит, чтобы
они совпадали с раскладкой.

---

## 1. Установка

Нужен узел, где стоит панель 3x-ui (панель и ядро уже работают), root и Python 3.11+.

С рабочей машины, где лежит этот каталог, — одной строкой:

```bash
rsync -a --exclude .venv --exclude .git --exclude __pycache__ ./ root@УЗЕЛ:/opt/xray-client-balancer/ \
  && ssh root@УЗЕЛ /opt/xray-client-balancer/install.sh
```

Если код уже на узле — просто:

```bash
/opt/xray-client-balancer/install.sh
```

Скрипт создаёт каталоги, ставит зависимости (`httpx`, `pydantic`, `PyYAML`), кладёт
команду `xcb`, systemd-юнит и первичный `env`-файл. Запускать его повторно можно
сколько угодно: это обновление кода, конфиг, токен и база назначений не трогаются.

Ключи: `--start` (сразу включить службу), `--src DIR` (взять код из другого каталога).

## 2. Настройка: три шага

### Шаг 1. Создать исходящие в панели

Панель → «Исходящие»: добавить те, через которые должен ходить трафик — например
два-три основных сервера и один резервный. Запоминать их теги не нужно, сервис прочитает
их сам, в том числе те, что приходят из подписок панели.

### Шаг 2. Положить токен панели в env

Панель → Настройки → Безопасность → API-токены → создать токен и вписать его в файл:

```bash
nano /etc/xray-client-balancer/env      # XRAY_BALANCER_API_TOKEN=<токен>
```

Файл уже создан установщиком, права 600. В самом конфиге токен не хранится — только имя
переменной окружения.

> Про токен: панель показывает его один раз, дальше хранит лишь SHA-256. Команда
> `x-ui setting -getApiToken -tokenName ИМЯ` не «показывает», а **перевыпускает** токен —
> предыдущий сразу перестаёт работать. Поэтому заведите сервису отдельное имя и держите
> значение в `env`; после перевыпуска обновите файл и перезапустите службу.

### Шаг 3. Запустить `xcb init`

```bash
xcb init
```

Сервис читает исходящие панели (шаблон + собранный конфиг ядра), показывает их списком и
спрашивает, какие взять:

```
Исходящие панели (5):
  1) sub1-mskserv   vless   185.x.x.1:443     [шаблон+ядро]
  2) sub2-cringe    vless   185.x.x.2:443     [шаблон+ядро]
  3) sub3-riga      vless   riga.example:443  [шаблон+ядро]
  4) sub4-stock     vless   185.x.x.4:443     [шаблон+ядро]

Шаг 1. Какие исходящие сделать балансировщиками?
  Номера: 1,2,3
Шаг 2. Какой исходящий сделать общим резервом (fallback)?
  Номер: 4
```

Дальше всё делает сам: пишет `/etc/xray-client-balancer/config.yaml` с выбранными тегами
и сразу создаёт в панели балансировщики `client-balancer-1..N`, правила `routing` и
участок healthcheck, без которого резерв не работает. Руками в панели править ничего не
нужно.

Без вопросов (для скриптов и повторной настройки):

```bash
xcb init --list-only                                          # только показать исходящие
xcb init --primary sub1-mskserv,sub2-cringe --fallback sub4-stock --yes
xcb init --force            # переписать существующий config.yaml (старый сохранится в .bak)
```

Если панель стоит на этом же узле, URL определяется сам (из `/etc/x-ui/x-ui.db`), иначе
передайте `--panel-url https://127.0.0.1:21868/base-path/` или положите
`XRAY_BALANCER_PANEL_URL=...` в `env`.

Осталось включить постоянную синхронизацию:

```bash
systemctl enable --now xray-client-balancer
xcb status
```

## 3. Команды

| команда | что делает |
|---|---|
| `init` | найти исходящие, выбрать нужные, создать `config.yaml` и применить в панели |
| `outbounds` | показать исходящие панели (`--all` — вместе со служебными, `--json` — машинно) |
| `status` | раскладка, правила, живые балансировщики, время последней синхронизации |
| `clients` | клиенты с id и группой (`--filter`, `--group`, `--offline`) |
| `balancers` | группы сервиса: свой исходящий, стратегия, число клиентов (`--live`) |
| `move` (`assign`) | перевести клиента(ов) в другую группу; без `--yes` — только план |
| `rebalance --yes` | заново разложить всех ровно (отменяет ручные переносы) |
| `reset --yes` | **полная перенастройка с нуля** одной командой (см. §6) |
| `sync` | одна синхронизация (`--dry-run`, `--force-write`) |
| `daemon` | цикл синхронизации; это и запускает systemd-юнит |
| `doctor` | замеры: память процесса, файлы состояния, место на диске (ничего не меняет) |
| `check-api` | диагностика API панели: 8 проверок, ничего не пишет |

`xcb` — это `/usr/local/bin/xcb`, обёртка: читает токен из `env` и вызывает модуль из
`/opt/xray-client-balancer`. Глобальные ключи (`--config`, `--log-level`) работают и до,
и после имени подкоманды.

## 4. Повседневная работа

```bash
xcb status                     # кто где и что с балансировщиками в ядре
xcb clients                    # список с id и группой
xcb move anna@example 2        # план: anna -> client-balancer-2
xcb move anna@example 2 --yes  # выполнить
xcb move --to client-balancer-1 anna@example bob@example --yes
xcb move anna@example --auto --yes     # в самую свободную группу
xcb move --id 17 --to 3 --yes          # по внутреннему id (email поменяли — id тот же)
```

Перенос меняет назначение клиента и одно-два правила `routing`; такие правки панель
применяет без перезапуска ядра, и команда печатает uptime ядра до/после — видно, что
разрыва не было. В конце печатается готовая команда возврата (`xcb move <email> <прежний
тег> --yes`).

Коды выхода `move`: `0` — сделано или показан план, `1` — ошибка (панель недоступна,
конфиг не принят), `2` — отказ по существу (клиента нет, подстрока неоднозначна, тега нет,
клиент исключён). Отказ не пишет ни в панель, ни в базу.

Если `xcb` не под рукой, те же команды доступны напрямую:
`/opt/xray-client-balancer/.venv/bin/xray-client-balancer status`.

## 5. Защиты

* перед каждой записью шаблон панели сохраняется в `/var/lib/xray-client-balancer/backups`
  (хранятся последние 20) — это же материал для отката;
* перед записью конфиг перечитывается и сравнивается «чужая часть» (правила и секции, к
  которым сервис не имеет отношения): если админ правил конфиг в этот момент, цикл
  отменяется, а не затирает его;
* кандидат проверяется до записи: существуют ли нужные исходящие, у балансировщиков ровно
  один `selector`, нет пустых правил и дублей клиента в двух группах; при включённом
  `validation.local_xray_test` — ещё и `xray run -test`;
* если после записи ядро не поднялось (`safety.xray_ready_timeout`, 30 с), конфиг
  автоматически возвращается к предыдущему, событие пишется как CRITICAL;
* если панель ответила пустым списком клиентов, а назначения в базе есть — синхронизация
  отклоняется и ничего не удаляется (`safety.refuse_empty_panel`);
* если конфиг приходится починять `safety.churn_breaker_cycles` циклов подряд,
  автоматические записи останавливаются до `xcb sync --force-write`.

Сервис трогает только своё: правила с `balancerTag` из своего конфига (и/или комментарием
`xcb-managed:<тег>`), свои балансировщики и свои теги в секции healthcheck. Чужие правила,
балансировщики, `domainStrategy`, `log`, `dns`, `policy`, inbound'ы и outbound'ы — не
трогает никогда.

## 6. Полная перенастройка с нуля

```bash
xcb reset          # план: что будет снесено и на что разложится заново
xcb reset --yes    # выполнить
```

Одной командой: убирает из конфига панели все балансировщики и правила сервиса (включая
правила групп, которые вы удалили из `config.yaml`), очищает локальные назначения и
защитные счётчики, раскладывает всех клиентов заново ровно по группам из текущего
`config.yaml` — и всё это одной записью в панель (с бэкапом).

Когда это нужно: после правки `balancers`/`fallback` в конфиге, переезда на другие
исходящие, или когда раскладка «запуталась» ручными переносами и хочется начать с чистого
листа. Точечный перенос одного клиента — это `move`, а не `reset`.

## 7. Обновление и удаление

```bash
# обновление кода (конфиг, токен и state.db не трогаются)
rsync -a --exclude .venv --exclude .git --exclude __pycache__ ./ root@УЗЕЛ:/opt/xray-client-balancer/ \
  && ssh root@УЗЕЛ '/opt/xray-client-balancer/install.sh && systemctl restart xray-client-balancer'

# удаление с узла
systemctl disable --now xray-client-balancer
rm -f /etc/systemd/system/xray-client-balancer.service /usr/local/bin/xcb
systemctl daemon-reload
rm -rf /opt/xray-client-balancer /var/lib/xray-client-balancer /etc/xray-client-balancer
```

После удаления раскладка в панели продолжает работать (сервис свои правила при остановке
не удаляет). Если нужно вернуть прежний конфиг — см. §8.

---

## 8. Откат

1. **Вернуть прежний routing.** Взять файл из `/var/lib/xray-client-balancer/backups/`
   (`{"saved_at":..., "template":{...}}`), вынуть поле `template` и записать его в шаблон
   панели (`POST /panel/api/xray/update`, form-поле `xraySetting`). Проще — не трогать
   ничего: сервис сам держит свой блок согласованным.
2. **Вернуть шаблон панели целиком** из бэкапа БД панели. Бэкап стоит один `cp` перед
   любыми работами:
   `TS=$(date +%F-%H%M%S); mkdir -p /root/xui-backup-$TS; cp -a /etc/x-ui/x-ui.db* /root/xui-backup-$TS/`,
   восстановление — `systemctl stop x-ui; cp -a /root/xui-backup-<ts>/. /etc/x-ui/; systemctl start x-ui`.

## 9. Если что-то не так

| симптом | причина | что делать |
|---|---|---|
| все `/panel/api/*` отвечают `404` с пустым телом | нет токена или неверный base path (панель скрывает эндпоинты за 404) | проверить токен в `env` и `panel.url` в `config.yaml`; `xcb check-api` |
| `401` | токен перевыпустили (`-getApiToken`) и не обновили `env` | вписать новый токен, `systemctl restart xray-client-balancer` |
| `sync` пишет `outbound 'X' отсутствует и в шаблоне, и в работающем конфиге` | тега нет ни в панели, ни в подписках | создать исходящий в панели; либо `xcb init --force`, либо поправить `balancers`/`fallback` |
| `init` не находит исходящие | их нет в панели | создать их в панели, затем `xcb init` |
| сразу после записи `routeTest` отвечает `xray is not running` | панель перезапускает ядро на каждой принятой записи, ядро ещё стартует | подождать 5–30 с; это помечается как «не проверено», а не как ошибка |
| CRITICAL `ядро Xray не поднялось после записи — выполняется откат` | конфиг отвергнут ядром | конфиг уже откачен; смотреть `xray/getXrayResult`, `journalctl -u x-ui`, свои `balancers`/`fallback` |
| CRITICAL `сработал churn-предохранитель` | три цикла подряд конфиг приходилось чинить (кто-то правит `routing` параллельно) | разобраться руками, затем `xcb sync --force-write` |
| служба циклически перезапускается | смотрите `journalctl -u xray-client-balancer -n 30` | чаще всего это токен или `panel.url` (код выхода 2) |

## 10. Конфиг

Живой конфиг — `/etc/xray-client-balancer/config.yaml` (создаётся `xcb init`, права 600),
полный образец со всеми ключами — `config.example.yaml` в репозитории. Главное:

| ключ | смысл |
|---|---|
| `panel.url`, `panel.api_token` | адрес панели и `${XRAY_BALANCER_API_TOKEN}` (значение — из окружения) |
| `panel.ca_bundle`, `tls_verify_hostname` | свой сертификат панели, если он самоподписанный |
| `balancers[].tag`, `primary`, `strategy` | группа, её единственный основной исходящий, стратегия Xray (`leastLoad` по умолчанию) |
| `fallback.outbound` | общий резерв для всех групп |
| `sync.interval_seconds` | период синхронизации (30 с) |
| `observatory.type` | `auto` / `observatory` / `burst` — какой healthcheck нужен ядру |
| `exclude_clients`, `exclude_regex` | клиенты, которых сервис не трогает вообще |
| `include_disabled` | оставлять ли в правилах выключенных/просроченных клиентов |
| `validation.local_xray_test`, `route_test` | проверять кандидата локальным ядром и маршрут через `routeTest` |

Пути по умолчанию: состояние — `/var/lib/xray-client-balancer/state.db`, бэкапы —
`/var/lib/xray-client-balancer/backups`.

## 11. Тесты

```bash
python3 -m pytest -q     # весь набор, включая интеграционный сценарий на mock-панели
```

`tests/mock_panel.py` — мини-панель 3x-ui на настоящем HTTP: авторизация по Bearer,
404 без токена, `obj` строкой, нормализация шаблона при сохранении, состояние ядра,
`routeTest` по правилам конфига. На ней проверяются распределение и его детерминизм,
удаление и переименование клиентов, переносы (`move`), перенастройка (`reset`), настройка
с нуля (`init`), автооткат при неподнявшемся ядре, идемпотентность и отказы при
недоступной панели.
